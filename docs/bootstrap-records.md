# Bootstrap records

The project preserves MIT LICENSE/NOTICE and uses one Bun application at `.`. The TypeScript/browser entrypoints are the approved target inventory during migration. Write `.bootstrap-lock.json` only after final validation; never hash unfinished output or claim replay from a missing record. Local shared skill and MCP installation details are recorded without redistributing their files.

Use baseline ID `wnz-repo-v1`. Adapt the pinned actual starter files as recorded in [quality.md](quality.md); manifests and native commands own executable policy. Missing information is a pending input, not permission to invent another preset. Existing repositories get a documented mapping to their current owners; conflicting existing requirements need an explicit decision before migration.

Resolve these inputs before creating dependent configuration:

| Input                 | Resolution rule                                                                                                                                                                                                                                                                                                                          |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Profile               | `python-single`, `typescript-single`, or `monorepo`; supplied by the user.                                                                                                                                                                                                                                                               |
| Component inventory   | Explicit unique name, relative path, language, artifact kind (`library` or `application`), and real entry points. Single repositories use path `.`; adapt the starter monorepo layout to the real inventory, using language-specific `packages/` directories and `apps/<name>` for applications.                                         |
| Python                | Exact patch version supplied for the project, at least 3.12; derive minor-version configuration from it. Do not silently upgrade an existing supported version.                                                                                                                                                                          |
| TypeScript target     | `bun`, `node`, or `browser` per component. Bun baseline is 1.3.13. TypeScript tooling and all Nx monorepos also require Node: default 24.19.0, with `@types/node` 24.19.2 for TypeScript. A required existing Node override must supply a compatible exact runtime/type pin; do not confuse the application target with the CLI runtime. |
| CI                    | Existing provider, or explicit choice for a new repository. Hosted runners unless self-hosted is selected. Required operating systems are explicit inputs; do not infer Linux verification from macOS.                                                                                                                                   |
| Features              | Per-component `none`, `pending`, or `resolved` state for validation, Python LLM work, and MCP work; MCP client protocol and transport requirements; actual Python provider extras.                                                                                                                                                       |
| Optional integrations | Each has `pending`, `include`, or `exclude` plus the requested details. Pending choices never change local or remote settings.                                                                                                                                                                                                           |
| Skills                | Trusted source, immutable commit or installed-content digest, source subdirectory, license, destination, and selected client discovery mechanism for each required skill. No mutable `main` source or unverified download counts as a pinned installation.                                                                               |

Write the resolved inputs and `baseline: "wnz-repo-v1"` to root `.bootstrap.json`. Its component list is the inventory used to generate workspace membership, native commands, Nx projects, and verification. It must contain no credentials. Record option answers there, including the target client and `repository` or `user` scope for Serena and semantic MCP configuration. Represent client config locations with repository-relative or portable home-relative paths, not another workstation's absolute username/path. A user-scope change still needs authorization. Missing executable, authentication, source, or registration permission makes an included feature incomplete; never switch it to excluded silently.

Use these exact top-level keys: `baseline`, `profile`, `purpose`, `license`, `documentationLanguage`, `runtimes`, `components`, `ci`, `options`, and `skills`. License is the supplied SPDX identifier or `pending`; never infer the target project's license from the starter's CC0 license. Create the project's LICENSE file only after its choice resolves. Documentation language is explicit; ask when unknown. `runtimes` has `python`, `uv`, `bun`, `node`, and `nodeTypes`, each an exact version string or null when unused. uv is also needed for isolated ShellCheck tooling in TypeScript-only repositories that contain shell hooks.

Each component has `name`, `path`, `language`, `target` (`bun`, `node`, `browser`, or null for Python), `artifact`, `importPackage` (Python only; otherwise null), `testDependencies`, `validation`, `entrypoints`, `runtimeDependencies` (names of components reached through runtime contracts), `llm`, and `mcp`. TypeScript `testDependencies` is an explicit map of actual test-harness packages to their declared versions, also present in the component's devDependencies; it excludes root quality tooling. It defaults to `{}` for Bun's built-in runner. Python uses its manifest's `test` dependency group and records null here. Feature objects always have `state: "none" | "pending" | "resolved"` and the user's `answer` (text or null). `llm` additionally has `providers` (objects with `name` and provider `extras`); `mcp` additionally has `protocol`, `transport`, and `clients`, nullable while pending. `validation` records whether an external-data boundary requires Pydantic. None means explicitly absent; pending is never serialized as none, an empty provider list, or null. A resolved LLM/MCP feature requires its provider/transport/client details before dependent generation. Independent quality setup can proceed with feature states pending, but complete setup cannot be claimed.

`ci` has `provider`, `operatingSystems`, and `actionRevisions`. `options` has exactly `promotion`, `merge`, `cloud`, `serena`, `semanticMcp`, and `selfHostedCi`, each an object with `state`, `answer`, and `details`. Option states are `pending`, `include`, or `exclude`; answer is the user's text or null. Details are null while unresolved. Each `skills` entry has `name`, `source`, `revision`, `subdirectory`, `license`, `digest`, and `discovery`.

Validate all resolved fields before generation: versions are exact, names and paths unique, paths relative and contained in the repository without `..`, languages/targets/artifacts are from the declared enums, and each included option has its required details. `promotion.details` contains branch/environment names and promotion rules; `merge.details` contains strategy and both cleanup booleans; `cloud.details` contains provider/accounts/projects/credential method/local-versus-CI scope; Serena/semantic details contain client, scope, version/revision, and config location; self-hosted CI details contain host, lifecycle, isolation, and access rules. Pending or excluded options have no generated configuration. An include answer with missing details stays pending. Reject unknown keys instead of silently discarding spelling errors. Sort components by path and skills by name for generated inventories; use two-space JSON indentation and a final newline.

Generate in this order: resolve inputs, render configurations/helpers, initialize language lockfiles and install pinned tools, format generated source/configuration, initialize consumer-isolation lockfiles, verify all gates, then calculate file digests and write `.bootstrap-lock.json` last. Exclude `.bootstrap.json` and `.bootstrap-lock.json` from Prettier and serialize both as two-space JSON with sorted object keys, sorted inventories, and a final newline. Do not format recorded files after hashing without recalculating their digests. Record exact direct dependency versions, tool executable versions, skill revisions/digests, and configuration SHA-256 digests. Keep records in version control when commits are authorized. Do not put transient timestamps in generated configuration. Reuse records and all language/consumer lockfiles on repeat execution. Compare current file digests before overwriting: preserve local edits and resolve differences rather than resetting them.

The lock record has exactly `baseline`, `specificationSha256`, `runtimes`, `dependencies`, `skills`, and `files`. For starter releases after v1.0.0, hash the exact local `docs/bootstrap-records.md` bytes as `specificationSha256`. This document owns the record contract; `files` covers the concrete policy and other generated content. A changed contract requires an accepted revision before regeneration. The v1.0.0 release instead hashed the original website specification; preserve that release record on replay unless migration is accepted. `dependencies` maps manifest-relative paths to objects of direct name/version pairs. `skills` maps skill names to immutable revisions and content digests. `files` maps generated repository-relative paths to SHA-256 values, excluding the lock record itself. A skill digest is SHA-256 over sorted relative file paths and their byte digests, excluding caches. Do not include build products or local state. Lock records are refreshed only for explicitly accepted input, baseline, dependency, or generated-content changes.

Fixed configuration and direct tool pins make policy repeatable. Transitive dependency resolution on the first run can still change with registry contents; full dependency replay requires the resulting `uv.lock` and `bun.lock`. Do not claim byte-identical installs across platforms or new lockfile resolutions.

The local writer serializes each skill digest input as sorted UTF-8 relative paths, a NUL, the lowercase SHA-256 byte digest and a newline. Cache files are excluded. `bun --no-env-file tools/records.ts` refreshes accepted inventory and covered-policy digests; it is an explicit mutation command, never a check or automatic setup step.

Skill names are single directory names under the shared skill root. The explicit writer rejects traversal, root/ancestor aliases and symbolic links before enumerating or reading skill inputs. Public policy inputs likewise require regular files with matching canonical paths before hashing.
