## High-level design and rationale

Keep one application manifest. `src/server` owns HTTP/startup, `src/sidecar` owns source adapters and controls, `src/browser` owns browser behavior, and `src/shared` owns the actual cross-runtime data contracts and scene-role table. Keep module factories and injected clocks/process adapters already present. Convert globals into direct imports; expose a named browser mount function for deterministic tests. Avoid a new service framework, event framework, generic dependency container or generated API client.

Keep authored static resources under `frontend/`; only executable JS moves. This avoids moving ignored private artwork. A build creates `dist/runtime` and `dist/public`; it never clears source assets or local state. Compiled server code uses an explicit installation root and public root. Root configuration defaults are derived from that installation root rather than a relocated module's directory.

The local build copies every installed pack from `frontend/assets/themes`, including ignored packs, after containment checks. Packaging uses a separate clean staging root containing only tracked public assets and the canonical pack. Never pack the local `dist` blindly. A user-selected pack is validated by existing startup rules; build does not silently substitute the canonical pack. Packaging cannot overwrite local dist or private inputs.

Browser build uses Bun. One small synchronous IIFE applies theme variables in the HTML head after the nonce bootstrap. One ESM main bundle imports browser modules and mounts the app after the document exists. Shared theme logic is side-effect-free; the head entry and main entry use the same validator/normalizer, and only the head entry performs prepaint application. Keep the server-injected window fields typed; remove all other application globals.

- Design choices: retain frontend assets and root local configuration to reduce migration risk; use Bun build for browser output and TypeScript emission for unbundled Bun modules so worker/native relative paths remain explicit; treat installed application startup as the consumer contract rather than inventing a library API.
- Risks and safeguards: type-only changes can alter absent/null behavior, process cleanup and UI timing. Characterize these first, migrate in dependency order, and preserve strict runtime checks. A clean build stages output before replacing generated files. It never removes local config, rooms or theme directories. Rollback is reverting the feature changes and rebuilding; original local inputs remain usable.
- Open decisions: optional integrations and cleanup policy remain pending as listed in DISCOVERY.md. Main target and merge commits are already decided. Proposed hosted CI is GitHub Actions on Ubuntu plus macOS, using pinned action revisions. Fixture-backed browser checks run on the available supported host; native checks run on a matching supported local or CI runner; any check involving real agents, SSH hosts or opt-in controls needs explicit live-run authorization. A required unrun live check prevents a claim that the live behavior was verified.
