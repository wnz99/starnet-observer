### F1: Recognize the current supported Codex footer while browsing

- Problem and current behavior: the affected working pane now renders `New activity · enter/esc latest · ? shortcuts`. The current parser rejects this final row before requesting process evidence. Its blank first row and unique thread-ID second row still satisfy the remaining grammar.
- Proposed behavior: also accept this exact UI-authored navigation form, with `enter/esc latest` or `esc latest`, while preserving existing shortcuts forms and all other parser conditions.
- Effect on the code: extend only `evidence.ts:footerRows`; do not add transcript scanning or renderer inference.
- Scope and compatibility: support observed Codex 0.163 default-key footer forms. Arbitrary search, selection, copy, loading and unknown/custom-key footers remain unavailable unless already accepted by the current grammar. No general compatibility framework.
- Acceptance outcomes: normal and navigation footers resolve through the full proof. Wrong row, multiple UUIDs, control characters, malformed navigation and scrollback substitutions remain rejected.
- Execution mapping: Task 1.

### F2: Obtain fresh identity through ordinary redraw contention

- Problem and current behavior: each complete capture starts Python twice. The final content revision must match the revision before the accepted footer. Ordinary output often invalidates this long bracket.
- Proposed behavior: use one lazy private Python process for fresh libproc queries, then retry at most twice after an exact content conflict. Repeat the entire proof; never cache births or reuse rejected footer text.
- Effect on the code: replace process-reader implementation, add disposal to existing observer lifecycle, and wrap the existing single capture in a bounded loop.
- Scope and compatibility: existing Python dependency and Herdr 0.9.1 methods. Preserve `readProcessBirth` injection and local-macOS capability restrictions. Existing `execute` injection continues to supply configuration reads; birth fixtures move to the dedicated reader/client seam.
- Acceptance outcomes: a conflicted attempt followed by a valid complete attempt resolves/revalidates. Terminal replacement, PID reuse, changed conversation, persistent contention and missing proof remain unavailable.
- Execution mapping: Tasks 2, 3 and 4.

### F3: Distinguish exhausted contention from capability failure

- Problem and current behavior: decoder discards `stale_content`, producing generic identity warnings. Fail-open counts aggregate across panes since startup.
- Proposed behavior: recover bounded content conflicts silently; classify exhausted contention with one static diagnostic per logical operation. Keep real socket, process, malformed-response and timeout failures visible.
- Effect on the code: preserve one safe internal code at the socket boundary and classify at existing resolve/revalidation boundaries; reuse current throttling.
- Scope and compatibility: no public diagnostic schema, per-attempt logs or raw upstream error messages. Content conflicts remain pane-local.
- Acceptance outcomes: only exact correlated codes trigger retries. No private IDs, paths or text enter diagnostics. True capability failures retain refresh suppression.
- Execution mapping: Tasks 3 and 4.

### F4: Reduce healthy-path cost and prove the performance tradeoff

- Problem and current behavior: the initial `agent.get` validates incarnation, and a later `pane.get` separately obtains geometry although its response also contains incarnation. Healthy captures use nine socket requests and two fresh process reads; retrying alone would increase load.
- Proposed behavior: validate initial incarnation and geometry from one `pane.get`, before the first fresh birth. Keep the post-footer terminal read and both births. Healthy capture uses eight socket requests, no extra process queries, and no process spawn after the helper's first request.
- Effect on the code: combine the initial probe/ownership read in the existing capture RPC owner; update explicit sequence, schema and load assertions. Compare healthy latency and bounded contention work under identical synthetic conditions.
- Scope and compatibility: use fields present in Herdr 0.9.1 and confirmed by the controller on the installed endpoint. Missing/mismatched fields fail closed. Do not add caches, polling services, concurrent proof reads, public settings or a benchmark framework.
- Acceptance outcomes: eight RPCs and two fresh queries per successful first attempt; twenty-pane healthy refresh uses 160 RPCs rather than 180. Same-workload virtual publication is at most 1500 ms, retaining two-second polling and six-second freshness. Resource receipts report scoped wall/CPU/peak-memory costs and failure/load limits without inventing a live latency SLA.
- Execution mapping: Tasks 3 and 4.

The existing Python ctypes/libproc query reused in one subprocess returned 50 valid identical births: first 47.197 ms; warm mean 0.030 ms; maximum 0.130 ms. This removes Python startup from the protected content bracket without experimental bindings. A subsequent full-pipeline comparison on the target was rejected at the first footer read, so produced **no valid guarded samples** and says nothing about helper effectiveness. It exposed F1 instead. ### Proof and retry policy

Current-session ownership is the invariant; freezing every unrelated PTY byte is conservative implementation machinery. This plan retains it because removing repeated startup and bounded retries offer a smaller evidence-backed improvement without replacing the proof.

Each accepted attempt uses this order: recent-footer preflight; one `pane.get` validating expected terminal and geometry; fresh initial birth; initial even content revision; accepted recent footer; configuration recheck; fresh `agent.get` validating terminal; fresh final birth; final conditional revision probe. No awaited input follows the final probe. A retry restarts all of this with the same expected terminal. No evidence survives from a rejected attempt. Revalidation still compares session and birth against the original proof; inspector keeps before/after validation and final synchronous current-owner checks.

Herdr's [PaneInfo schema](https://github.com/herdrdev/herdr/blob/v0.9.1/src/api/schema/panes.rs) includes `pane_id`, `terminal_id`, `agent` and `scroll`; [handle_pane_get](https://github.com/herdrdev/herdr/blob/v0.9.1/src/app/api/panes.rs) returns that pane information for the requested pane. Controller read-only verification confirmed these fields on installed 0.9.1. Apply the existing `incarnation`/`sameTerminal` and geometry validators to that same response. Geometry supplies only the revision-probe coordinate; accepted footer text still comes from a separate recent read inside the unchanged content bracket. Moving geometry before initial birth adds no trust in its freshness: it remains bounded, is not transcript identity evidence, and invalid coordinates fail closed. Resize/replacement/ABA tests must cover this longer pre-revision interval. The final independent terminal/process/content checks remain mandatory; the initial response cannot replace them.

- Maximum three complete attempts per `Capture.capture` call. Retry only the safe internal code `IDENTITY_CONTENT_CHANGED` from a correlated structured `stale_content`, or the existing validated final-revision mismatch. Every other unavailable result/error stops immediately.
- Retry-start budget: admit extra attempts only within 1500 ms from this capture's start, using injected clock and existing `TIMEOUT`. This is **not a hard whole-capture deadline**. An admitted attempt may finish later; each RPC and process query keeps its own 1500 ms bound. No cancellation API expansion.
- Shared refresh admits at most eight extra complete attempts, derived from two extras per existing four workers. Store one remaining count in existing `RefreshState`, consumed synchronously immediately before starting each extra attempt. Every pane retains its ordinary first attempt unless current endpoint/capability suppression applies.
- Standalone resolves/revalidations remain capped at three attempts. Two inspector validations use at most six complete attempts, 48 capture RPCs and twelve birth queries. A refresh with N eligible panes uses at most `8*N+64` capture RPCs and `2*N+16` birth queries; unchanged configuration reads are additional work. For twenty panes, healthy load is 160 RPCs/40 birth queries; maximum retry load is 224 RPCs/56 queries, instead of tripling the entire roster. Early failures reduce these bounds.
- Recovered conflicts produce no warning. Exhaustion returns `content-changed` with one static diagnostic. No stale native fallback, background retry, user knob or success promise under sustained mutation.

### Private native-query process

Keep one lazy guarded `python3 -I -u -c <fixed script>` child per resolver in `birth.ts`. Reuse the current ctypes/libproc query and size/PID checks. No installed service, file registry, listener, compiler, package dependency or native binding. Spawn before the initial content revision at the first fresh birth read.

Private newline JSON request: `{request:positiveSafeInteger,pid:positiveInt32}`. Reply: `{request,birth:null|{pid,startSeconds,startMicroseconds}}`. One active query, FIFO maximum eight active/queued requests. Reject excess demand without writing or killing the healthy child. Each admitted request expires 1500 ms after enqueue. Each response line and unfinished buffered line is at most 1024 bytes. Correlate request and PID and use `validBirth`; never cache results. A valid null is PID-local and does not suppress healthy panes. Ignore stderr and never log raw frames/errors.

Malformed, oversized, duplicate, uncorrelated output, timeout, write/spawn failure or child death invalidates the generation and rejects its pending requests with a static capability error. Kill/close old child and ignore its late output. Later demand can restart only after confirmed exit; refresh suppression prevents a restart loop in the failed refresh. Parent pipe EOF exits Python. Idempotent `close` marks closed, rejects work, prevents spawn and sends SIGTERM; force SIGKILL after 100 ms if needed. Await exit for at most the existing 1500 ms `TIMEOUT`; failure to confirm exit rejects close with a static error and never permits replacement. The actual resolved identities adapter is closed by existing observer lifecycle. Idle child and pipe handles must not keep a standalone resolver's parent alive; retain handles while a request/close is pending. Test-owned clients close in `finally`.

Risks: extra protocol and lifecycle ownership are real costs, bounded to this domain client. Avoiding production FFI and compiled distribution justifies them. The host SDK `sys/proc_info.h:proc_bsdinfo` and `libproc.h:proc_pidinfo` match existing 136-byte ctypes layout. Preserve fresh native query and returned-PID validation, guarded child environment filtering, and exported-variable behavior.
