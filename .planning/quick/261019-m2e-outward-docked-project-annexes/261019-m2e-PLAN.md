# Outward-docked project annexes implementation plan

Semantic revision: 1. Status: authored and self-reviewed; simplicity review, independent plan review, annotation offer and user implementation approval remain pending. Requirements: [DISCOVERY.md](DISCOVERY.md). Planning authorizes no implementation.

## Features and effects

Overflow rooms will sit beside their own project, joined in a straight outward chain. A left-bank project grows left; a right-bank project grows right. The project’s original room stays anchored, while its annexes keep their existing names, sections, seats and project color.

### F1: One visible project family

- Problem and current behavior: every room, including an annex, receives its own station slot. A project and its `+1` room can appear across the station or on different decks.
- Proposed behavior: the parent owns one stable slot and all its annexes share that slot’s bank, row and deck. For example, a left-bank PERSONAL parent has PERSONAL +1 immediately left of it, then PERSONAL +2 farther left.
- Effect on the code: allocation continues to own section and seat identities; scene placement translates each annex outward from the parent’s origin.
- Scope and compatibility: preserve three blocks per room, eight root seats per block, checkout/folder grouping, helpers and host-scoped project identity. Parent slots remain stable during growth, reorder and removal while the project remains live. Existing annex positions intentionally change once on adoption. A reload rebuilds the in-memory layout; no persisted allocation migration is needed.
- Acceptance outcomes: growth through 24, 25 and 49 roots creates the expected rooms without moving existing parent desks; sections can also open an annex before 25 roots. Every room and helper in a project has the same `pageFor` result. Unrelated surviving projects retain slots and colors.
- Execution mapping: Task 1; Task 2 verifies the complete application.

### F2: Connected, accurately routed annexes

- Proposed behavior: each annex has one link to its inward neighbor. Mail travels from its desk through those links to the parent’s existing connection and its own host’s mailroom. Project-colored bridge trim makes the relationship visible. Amber relay cues retain their existing meaning.
- Effect on the code: room geometry supplies the same chain waypoints to walkway construction and worker routes. Existing courier endpoints consume those worker routes without acquiring a separate annex routing system. Both procedural station and home-office rendering draw project trim.
- Scope and compatibility: preserve per-room signs, repository selection, worker selection, inspector behavior and individual platform zoom. Ordinary idle movement stays within each worker’s existing platform/section; this change does not introduce inter-room wandering. Shadows remain hover-only and cannot gain control or inspection targets.
- Acceptance outcomes: a two-annex route traverses +2, +1 and parent front links in that order, ends at the proper mailroom, and never cuts through a room’s desks or walls. Every route segment has a matching room/apron/walkway surface. Relay members retain amber routing all the way through the shared path.
- Execution mapping: Tasks 1–2.

### F3: Expanded ships remain usable and separate

- Proposed behavior: hulls and overview fit include the entire chain. Observed ships keep their column; shadow ships move east as needed to clear expanded observed and shadow hulls.
- Effect on the code: ship placement estimates use actual room placement, replacing fixed shadow-width assumptions. Existing hull and camera consumers continue to use scene geometry.
- Scope and compatibility: preserve observed/shadow host separation, stream health, relay verification state, mailroom ownership and observation-link semantics. No server, protocol, configuration, theme-manifest or runtime dependency changes.
- Acceptance outcomes: local, remote and shadow annexes stay inside their own hulls; all host hulls are disjoint with existing gaps preserved or increased. Overview contains outermost bridges; selection and room zoom reach annex workers even on later decks.
- Execution mapping: Tasks 1–2.

## High-level design and rationale

Retain the existing allocation model, room size, section layout, art and navigation. Change the source of room slots to parent rooms only. Derive annex coordinates from that parent slot and the existing annex number. Use one small scene placement module for the coordinates consumed by both ship placement and room construction. Avoid a general docking graph, new persistence, branching, side-door wall surgery or a second camera mode.

Each 20-unit-wide annex sits four units beyond its inward neighbor. Parent positions retain the current local and remote formulas. Links run along the clear front aprons at the existing elbow depth, three units beyond the room’s front edge. This preserves the rear walls and furniture and reuses the existing front entrance. The connector between neighboring entrance elbows is 24 units long; the visible gap between room slabs is four units. This is a short front link between adjacent modules, not a corridor across the station.

Every annex has its own entrance stub and one horizontal link to its predecessor. Its worker route is its existing chair-to-entry prefix followed by those chain elbows, the parent’s existing spine join and mailroom suffix. Only parent rooms register direct spine joins. Build chain routes by project and annex index, independently of incoming room order; keep the existing output ordering for consumers. If lower-index room units are retained empty because a later block remains occupied, retain their physical modules and paths. Do not silently compact blocks.

Relay eligibility belongs to rooms and path segments. A bridge carries amber if any relay member must traverse it from that annex or farther out; the parent connector and bank spine carry amber if any room in that family requires them. Keep platform relay signs tied to each room’s own members. Project trim is a separate stroke, so project identity never replaces the amber relay signal.

**Approval-visible pagination decision:** a deck keeps eight project anchors per host; annexes no longer consume additional anchors. Families therefore stay on one deck, and a deck can contain more than eight room slabs. This can reduce deck count and make overview zoom smaller for large families. It preserves all seats, section capacity and per-project color uniqueness, and avoids hiding the parent or duplicating rooms across pages. Existing saved page numbers continue through the application’s current range clamp. Approving implementation must include this change; if an eight-slab hard page cap is required, return to product design rather than split a family silently.

Risks and safeguards:

- Very large families make a wide scene. Reuse overview fit, individual room zoom, worker focus and the existing bounded static-cache policy. Test a three-module chain and a wider stress fixture; add no speculative packing or optimization framework.
- Shadow hulls can overlap later observed rows when they are tall. Compute shadow clearance against every already placed hull whose vertical interval overlaps, not merely the shadow’s associated member. Preserve existing minimum offsets where they already suffice.
- Slot ownership changes old annex/deck assertions. Replace those assertions with family placement and unchanged seat/color requirements; do not weaken unrelated checkout, helper or host tests.
- Geometry and color changes must invalidate cached scene art. Include walkway geometry and project trim in scene revision evidence; verify label-only updates and theme parity remain correct.
- Rollback is a code revert. All allocation and scene state is ephemeral; no data/schema conversion or live action is required.
