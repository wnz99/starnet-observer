## Features and effects

llm-bus "coordinator mode" records which agent coordinates a project, which workers are enrolled, what they claimed,
which PR gates were submitted and which owner decisions are pending. The observer reads none of it today. After this
change the station shows that structure: coordinators sit on a bench in the observatory, a click on one lights up its
team across the rooms, coordinator mail visibly travels from the observatory through the mailroom to worker desks, and
the observatory screens, plates and a side panel show the coordination state. Everything stays read-only, bounded,
redacted and limited to agents the observer already identifies by exact pane join.

### F1: Coordinator bench in the observatory

- Problem and current behavior: the observatory has one desk and chair, used only by the overseer
  (`src/browser/scene/crew-topology.ts:seatOverseer`). A coordinator is drawn as an ordinary worker at its room desk.
- Proposed behavior: every observed coordinator of a coordinated project sits on a bench of up to 4 seats in the
  local observatory, next to the overseer desk. A coordinator observed on a remote host sits on the same bench with a
  host tag (for example `★ ops@buildbox`). Coordinators beyond 4 stay at their room desks and still carry the star.
  If the overseer itself is a coordinator, it stays in the overseer chair and gets the star; it takes no bench seat.
- Effect on the code: the sidecar publishes coordination teams; the browser removes seated coordinators from room
  layout (as it already does for the overseer) and the scene seats them as observatory workers with role `coordinator`.
  Their desk and chair are painted by the existing per-worker loop (`src/browser/view/station-items.ts:StationItems.collect`
  → `desks()` and `chair()`), the same path that paints the overseer's desk today. Only occupied bench seats are drawn;
  unoccupied seat slots are geometry only.
- Scope and compatibility: no bench furniture without seated coordinators, so stations without llm-bus coordinator mode
  look unchanged. Presentation mode omits all coordination data.
- Acceptance outcomes: AC1.1–AC1.4.
- Execution mapping: Tasks 1, 2, 3, 4, 5.

### F2: Coordinator selection highlights the team

- Problem and current behavior: a sprite click selects one worker; the only group highlight is repository selection
  (`src/browser/view/frame-overlays.ts:FrameOverlays.repository`).
- Proposed behavior: clicking a coordinator sprite (bench seat, or room desk for bench overflow) selects it and
  highlights its whole team (coordinator plus
  every observed enrolled worker on the current page, in any room or ship) with a ring in the team crest hue; all other
  crew sprites are dimmed. The team spans hosts: llm-bus keeps one `project_id` for a project whose coordinator runs on
  another machine, so the local bus (workers, coordinator `external`) and the observed host bus (coordinator, workers
  `external`) are two halves of one team. The browser merges halves that carry the same team key, so clicking a remote
  coordinator on the bench lights up the local workers it directs, and the reverse. Gate records and grants live on
  the workers' machine (llm-bus stores them where the worker enrolled), so the merged team shows gate rows and grant
  expiry from every half, not only the coordinator's. Clicking the observatory floor or
  sign keeps today's overseer select/start behavior. Selecting anything else, or `Escape`/overview, clears the team
  highlight.
- Effect on the code: `AppState` exposes the selected team; the view reads it per paint through one new update callback.
  `coordinationView` owns the cross-bus merge (precedence under Design choices).
- Scope and compatibility: selection of a seated coordinator never changes page (same rule the local overseer uses).
- Acceptance outcomes: AC2.1–AC2.4.
- Execution mapping: Tasks 2, 3, 5, 7.

### F3: Coordinator mail couriers use the observatory link path

- Problem and current behavior: courier endpoints use a worker's `route` only when the worker has a layout seat
  (`src/browser/scene/mail.ts:endpoint`); other ids fall back to the mailroom chute.
- Proposed behavior: mail from or to a seated coordinator flies along its route: bench seat, observatory link path,
  mailroom hub, then the worker desk (and the reverse for replies). A remote-host coordinator's route continues from the
  local hub along that host's existing observation link to the remote mailroom hub, so that host's courier still sorts at
  its own mailroom.
- Effect on the code: `endpoint()` gains one branch for observatory-seated coordinator workers.
- Scope and compatibility: the overseer's existing chute behavior is not changed.
- Acceptance outcomes: AC3.1–AC3.2.
- Execution mapping: Tasks 4, 6.

### F4: Sealed directive and report couriers

- Proposed behavior: a message whose llm-bus coordination metadata matches the current coordination records is
  *sealed* and flies in the new `mail-sealed` colour. "Matches" mirrors every stored-record predicate of llm-bus
  `authorize()` for non-gate operations, in its order: valid direction (exact five keys, `version` 1, canonical UUIDv4
  ids, operation one of the six non-gate `OPERATIONS`); project found by the message's stored recipient scope and
  `project_id`, not revoked, same generation, sender is the project coordinator; a consent row for the grant is
  optional, but when present it must be unended and owned by the recipient; the recipient is enrolled in that project
  with the same generation; the grant matches scope, project, recipient and grant id, is not revoked, has the same
  generation and coordinator, has an `expires_at` that is null or a parseable RFC3339 time after now, and holds a valid
  operations list that contains the message's operation. Only the six non-gate operations (`assign, reprioritize,
  clarify, pause, cancel, review`) can be sealed. Gate operations (`approve-commit`, `approve-push`, `approve-merge`,
  `approve-merge-admin`) are never sealed: llm-bus authorizes them from approvals, gate records, delegations and peer
  configuration, which the observer does not mirror, so they keep today's colour. A message from an enrolled worker to
  its project coordinator is a *report* and flies in `mail-report`. All other mail, including coordination messages
  that do not match, keeps today's colour. Wire field: `messages[].coordination?: "sealed" | "report"`.
- Scope and compatibility: "sealed" is the observer's read of stored records, not llm-bus's full authority decision.
  For non-gate operations it omits only the live checks: the recipient's and consent owner's current agent scope and
  session end, and idle-agent expiry. It is deliberately stricter in three cases: gate operations are never sealed, an
  overflowed grants, consents or enrollments read seals nothing, and an unparseable expiry counts as expired. The panel
  and README say "matches current coordination records", never "verified by llm-bus".
- Acceptance outcomes: AC4.1–AC4.3.
- Execution mapping: Tasks 1, 2, 3, 6.

### F5: Decision beacon

- Proposed behavior: a seated coordinator with pending owner decisions in the current generation shows a pulsing
  `coordination-beacon` glow and a plate `? <count> · <countdown>` to the earliest deadline (`overdue` once passed, no
  countdown when no deadline). Any defaulted decision of the current generation adds a red `!` mark (`blocked` colour).
  Reduced motion keeps the plate and mark, without the pulse.
- Acceptance outcomes: AC5.1–AC5.2. Execution mapping: Tasks 1, 2, 3, 8.

### F6: Gate monitors

- Proposed behavior: the two observatory screens list the latest gate record per PR (up to 3 rows per screen, newest
  first, selected team first): `#<pr> <ticket> <status>` with submitted amber, accepted `done`, rejected `blocked`,
  superseded dim. A record that changes to `accepted` between snapshots flashes for 1.2 s (no flash under reduced motion).
  For a team whose coordinator runs on another machine, the rows come from the workers' machine, where llm-bus stores
  gate records, so they show and flash the same way.
- Acceptance outcomes: AC6.1–AC6.3. Execution mapping: Tasks 1, 2, 3, 5, 8.

### F7: Claim chips

- Proposed behavior: an observed worker with a claim shows a chip on its desk front: `<ticket> · <branch>` (clipped by
  the existing plate clipper). The existing repository desk badge keeps priority; a claim chip that collides is dropped
  by the plate priority system, never overlapped.
- Acceptance outcomes: AC7.1. Execution mapping: Tasks 1, 2, 3, 7.

### F8: Team crest

- Proposed behavior: each coordinated project gets a deterministic hue: `goldenHue(index)` over sorted team keys, the
  same function `FrameOverlays.repositoryColor` uses after extraction (one formula, two callers). Observed team
  members carry a small diamond badge in that hue above the head; the coordinator carries a star `★` in that hue.
- Acceptance outcomes: AC8.1. Execution mapping: Tasks 3, 7.

### F9: Coordination panel

- Proposed behavior: clicking a coordinator sprite also opens a coordination panel for its project in the existing
  panel stack (open, never toggle: a repeat or double click keeps it open; Escape and the stack close it). It shows
  label, objective (redacted, ≤ 512 chars), generation (short id), the worker roster (`claimed` with ticket/branch;
  `idle` = a usable current grant with no consent row or an unended consent owned by the worker; `no consent` =
  readable records but no usable grant or consent; `unknown` = grants or consents unreadable or overflowed) plus a count of
  unobserved enrolled workers on observed machines,
  earliest active grant expiry (minimum over every half of a cross-machine team), instruction and amendment counts, the latest instruction and latest amendment text
  (redacted, ≤ 512 chars), pending/defaulted decisions with question text (redacted, ≤ 240 chars) and gate rows. Any
  source table that could not be read shows "unavailable" rather than zero.
- Acceptance outcomes: AC9.1–AC9.2. Execution mapping: Tasks 1, 2, 3, 9.

### F10: Handover animation

- Proposed behavior: when a team's generation or coordinator changes between two snapshots, the bench seat of the
  (new) coordinator plays a 2.4 s handover sweep and plate `handover · gen <short>`; under reduced motion only the plate
  shows for 2.4 s. The first snapshot after load or resume never triggers a handover or a gate-accepted flash: changes
  made while the page was hidden are shown as state, not replayed as events.
- Acceptance outcomes: AC10.1. Execution mapping: Tasks 3, 5, 8.

## High-level design and rationale

One read model, three layers, all existing owners:

1. **Sidecar reader (SQLite worker)** — new `src/sidecar/bus/teams.ts:selectTeams` runs fixed, bounded, read-only
   queries on the same private bus snapshot copy the reader already makes (`src/sidecar/sqlite/snapshots.ts`). Each
   table query is wrapped independently (the pattern of `src/sidecar/bus/coordination.ts:readSection` and
   `src/sidecar/bus/overview.ts:aggregate`). It returns raw addresses (never leaving the worker/main boundary
   unvalidated) and classifies each windowed message as `sealed`/`report` (or leaves it unclassified). Every text field
   is read with one generous SQL `substr` bound and then clipped in JavaScript to a UTF-16 transport bound, the unit
   `validate-bus.ts:validTeams` counts. `selectRows` runs `validTeams` on the result itself and attaches `teams` and
   message kinds only when it passes, so a teams defect drops only teams and never makes the bus `unreadable`.
2. **Public projection (main process)** — `publicCoordination` (already the shared local/remote projection) adds a
   `teams` field: the input is checked with the same `validTeams` (as `validOverview` is today), addresses become
   observer endpoints through the existing exact pane join, free text is redacted with `redactText`+`cleanControls` and
   length-capped, and teams with no observed member are dropped. Because
   `src/sidecar/remotes/bus.ts:sanitizeBus` already calls `publicCoordination` with its host-remapping endpoint, remote
   hosts' coordination flows to `hostBus[host].coordination.teams` with no new transport. Presentation mode keeps its
   allowlist and omits teams and message kinds.
3. **Browser** — a pure derivation `src/browser/model/coordination.ts:coordinationView` turns local and host buses into
   per-worker and per-team facts once per snapshot (not per frame), merging the halves of one project observed on
   different buses by team key. `Floor` seats coordinators through `BuildOptions`,
   the scene adds bench geometry and coordinator routes, and the view paints signals from one `coordination()`
   callback, mirroring `repositorySelection()`.

- Design choices:
  - Name collision: the existing `src/sidecar/bus/coordination.ts` and the public `bus.coordination` container are the
    bus-panel diagnostics. **Decision: do not rename.** The public field is a wire contract with remote observers of
    other versions; renaming it would break mixed-version federation and churn bus-panel code for no behavior gain. The
    new concept is consistently named **teams** (`selectTeams`, `coordination.teams`, `CoordinationView`), which removes
    the ambiguity at every new identifier.
  - Coordinators are scene workers with `role: "coordinator"` instead of a new actor type, so movement, hit testing,
    selection, plates, desk/chair painting and couriers reuse existing code. `scene.workers` is the single owner of
    "which coordinators are seated": navigation, beacon anchors and the panel read it; no parallel id list is kept, and
    `revisionFor` already changes with worker ids and chairs (`src/browser/scene/revision.ts:revisionFor`).
  - "Sealed" is computed in the worker by mirroring every stored-record predicate of llm-bus
    `coordination/authority.py:authorize` for the six non-gate `OPERATIONS` (consent optional, as there; an
    `expires_at` that `models.py:timestamp` would reject counts as expired, as `authorize()` denies it). Gate operations
    are never sealed, because their `_gate_decision` path reads approvals, gate records, delegations and peer
    configuration that the observer does not mirror. An overflowed grants, consents or enrollments read seals nothing.
    It does not reimplement the live checks (agent scope/session state, idle expiry). The label states that narrower
    meaning. The worker roster's `idle`/`no consent` use the same grant and consent predicates.
  - Cross-machine teams: llm-bus imports a remote-coordinated project with the same `project_id` on every machine
    (`coordination/cli.py:_setup`/`_create`), so the published team key is derived from `project_id` alone and the
    browser merges teams with equal keys across the local bus and every host bus. Merge precedence (deterministic):
    halves are ordered local first, then hosts by ascending host id. The *owner half* is the first half whose
    coordinator is an observed row id, else the first half. Two fields follow where llm-bus stores the record, because
    gate records and grants exist only on the machine where the worker enrolled (`gate_records.py:submit` requires a
    local worker enrollment and claim; `store.py` join inserts the grant; `authority.py:_gate_decision` "Gate records
    stay local"): `gates` is the union of all halves' gate rows, keeping one row per PR — the greatest non-null
    `submittedAt`, a null `submittedAt` losing to any number, a tie going to the earlier half in merge order — then
    sorted by `submittedAt` descending and capped at 12; `grantExpiresAt` is the minimum non-null value over all
    halves, else null. Every other field — label, generation, objective, counts, latest texts, decisions and
    `sources`/`status`/`truncated` — comes from the owner half only, never mixed (so `sources.gates` and
    `sources.grants` describe the owner half). Workers are the union of
    observed ids from all halves, de-duplicated by id in owner-then-order sequence. A worker from a half whose
    `generation` differs from the owner's keeps its claim but gets status `unknown`. `unobservedWorkers` is the sum over
    halves (llm-bus enrolls a worker only on its own machine, `store.py:join_session`, so no enrollment is counted
    twice). Duplicate keys inside one bus cannot reach
    the browser (`selectTeams` keeps the first project per key).
  - Client-side transition detection (gate accepted flash, handover) compares consecutive snapshots in
    `AppState`, so the sidecar stays stateless and remote data behaves identically.
  - The panel opens on coordinator click (planner choice, reversible): the sprite click is the only entry point the user
    defined, and the existing panel stack already provides toggling, Escape and focus return.
- Risks and safeguards:
  - Worker transport: an invalid `teams` shape would fail the whole `bus.read` result (`src/sidecar/sqlite/worker.ts`
    replaces invalid results with "unreadable", and `validBusState` calls `validCoordination`). SQLite `substr` counts
    code points while JavaScript `.length` counts UTF-16 units, so one emoji-bearing label could exceed a unit limit.
    Safeguards: SQL reads at most `TEAM_LIMITS.readChars` (2048) code points, `selectTeams` clips every string to
    `TEAM_LIMITS.rawUnits` (4096) UTF-16 units without leaving a lone surrogate, and `selectRows` validates `teams`
    itself and omits `teams` and kinds on failure, so mail rows always survive. Tests cover astral text at every cap.
  - Older bus schemas: every query degrades on its own; `teams.sources` flags tell the UI which parts are unknown.
  - Privacy: raw addresses, scope paths, project/grant UUIDs, evidence/checks JSON, approvals and answers are never
    published. Team keys are domain-separated, unsalted pseudonyms (`sha256` of `["starnet-team-v1", project_id]`; the
    scope is excluded so the halves of one cross-machine project share a key), following `src/sidecar/bus/relay.ts`
    peer ids and `selection.ts:messageIdentity`. No salt is needed:
    llm-bus project ids are uuid4 values (`llm_bus/coordination/cli.py` `uuid4_string(... or uuid4())`), so the digest
    cannot be inverted or dictionary-matched, and it reveals nothing beyond a stable pseudonym. A per-process salt
    would change keys on every sidecar restart (crest hues reshuffle, flash/handover continuity lost); a persisted
    secret would add state the plan otherwise avoids. Every published text field (label, objective, question,
    instruction and amendment text, ticket, branch, class) is read with the same large SQL bound, redacted in the main
    process and only then capped to its display limit, the existing "scrub before the smaller display cap" rule
    (`selection.ts:selectInspection`). No field is cut to its display cap before redaction.
  - Identity: only exact `provider:session` pane joins (local) or surviving remote row ids (remote) produce agent ids;
    everything else is `external` and counted, never guessed.
  - Performance: derivation runs once per snapshot; paint reads precomputed maps; countdown text is the only per-frame
    computation; no work in input handlers beyond set lookups.
- Open decisions: none blocking. Planner-made, reversible choices: bench capacity 4; only occupied bench seats are
  drawn; panel opens on coordinator click;
  overseer-as-coordinator keeps the overseer chair; projects whose coordinator is unobserved on every observed bus show
  crests and chips but no bench seat or panel entry point; cross-machine merge precedence as stated above (the owner
  decision to cover the whole team across hosts is given; the owner fixed the gate union, minimum grant expiry and
  owner-half precedence for all other fields; the PR tie-break is the planner's).

## Data-flow analysis

| Stage | Input and source | Processing and owner | Output or side effect | Material failure handling |
| --- | --- | --- | --- | --- |
| Read | `coordination_*` tables in the private bus copy (untrusted, any schema age) | `bus/teams.ts:selectTeams`, fixed SQL with `LIMIT n+1`, `substr(…,1,2048)` on text, then JS `clipUnits(…, 4096)` | Raw teams with raw addresses; kinds map | Each query in its own `try`; failure sets its `sources` flag false; an overflowed grants, consents or enrollments read also sets its flag false (and `truncated`), so it never yields `sealed` or `idle`; projects query failure yields `status: "unavailable"` and no projects |
| Attach | `selectTeams` result | `bus/selection.ts:withTeams` runs `validTeams` | `BusState.coordination.teams`; `BusRow.coordination` kind | Validation failure or thrown error: no `teams`, no kinds; rows and sections unchanged |
| Transport | Worker result | `sqlite/validate-bus.ts:validCoordination` (calls `validTeams`) + `row()` | Accepted `BusState` | Cannot fail on teams: `withTeams` already validated with the same function |
| Publish (local) | `BusState`, observed rows | `bus/public-coordination.ts:publicCoordination` via `bus/public.ts:publicBus` | `bus.coordination.teams` with endpoint ids, redacted then capped text; `messages[].coordination` | Unobserved worker enrollments counted in `unobservedWorkers`; teams with no observed member dropped |
| Publish (remote) | Remote observer's public bus over SSH | `remotes/bus.ts:sanitizeBus` (same projection, host remap) | `hostBus[host].coordination.teams` | Older remote without `teams`: field absent; malformed: `validTeams` fails and `teams` is omitted; ids not in `rowIds` add to the input's `unobservedWorkers` |
| Presentation | Inventory | `presentation/mail.ts:makeMail` allowlist | No teams, no kinds | Unchanged behavior |
| Admission | Snapshot JSON | `browser/app/admission.ts` | Accepts optional `messages[].coordination` enum | Unknown kind rejects the snapshot like other enum fields |
| Derive | `bus`, `hostBus`, rows, transition baseline | `browser/model/coordination.ts:coordinationView` (merge by key: gates unioned, grant expiry minimum, other fields from the owner half); baseline chosen by `browser/app/render.ts` | `CoordinationView` | Malformed entries skipped individually; `previous: null` on first load and on the first snapshot after resume, so no flash or handover |
| Present | `CoordinationView`, scene | floor/scene/view/panel owners | Bench, team highlight, couriers, signals, panel | Missing data shows nothing or "unavailable" |

Public shape added to `PublicBus["coordination"]` (exact names, used by all tasks):

```ts
teams?: {
  asOf: number;
  status: "available" | "partial" | "unavailable";
  truncated: boolean;
  sources: Record<"enrollments" | "grants" | "consents" | "claims" | "gates" | "decisions"
    | "instructions" | "amendments" | "directives", boolean>;
  projects: CoordinationTeam[];
};
interface CoordinationTeam {
  key: string;                 // /^team_[a-f0-9]{16}$/, from project_id only; equal across machines
  label: string;               // ≤ 160
  generation: string;          // first 8 chars of the generation id
  coordinator: string;         // endpoint id or "external" / "ambiguous"
  objective: string;           // redacted, ≤ 512
  workers: { agent: string; status: "claimed" | "idle" | "no-consent" | "unknown";
             claim?: { ticket: string; branch: string } }[];   // observed only, ≤ 48
  unobservedWorkers: number;   // this machine's enrolled workers without an observed id
  grantExpiresAt: number | null;   // min over usable grants of this bus; browser merge takes the min over halves
  instructions: number | null; amendments: number | null;
  latestInstruction?: { audience: "coordinator" | "worker"; kind: "set" | "amend"; text: string; recordedAt: number | null };
  latestAmendment?: { text: string; recordedAt: number | null };
  decisions: { class: string; status: "pending" | "defaulted"; question: string;
               worker?: string; createdAt: number | null; deadlineAt: number | null }[];   // ≤ 8, current generation
  gates: { pr: number; ticket: string; status: "submitted" | "accepted" | "rejected" | "superseded";
           submittedAt: number | null; decidedAt: number | null }[];                     // ≤ 12, latest per PR
}   // browser merge: gates unioned over halves (latest per PR, ≤ 12)
// messages[] entries gain: coordination?: "sealed" | "report"   (absent for all other mail)
```

Raw worker-side shape (`RawTeams` in `src/sidecar/bus/types.ts`, a separate type from the public one) differs in four
ways: `coordinator`, `workers[].agent` and `decisions[].worker` hold raw addresses or endpoint ids; `workers` includes
every worker enrollment (≤ 48); every text field is pre-redaction and ≤ `TEAM_LIMITS.rawUnits` (4096) UTF-16 units;
`unobservedWorkers` is optional (absent in worker output, present when the input is a remote
observer's public teams). `validTeams` checks this raw shape; the public shape is a subset of it, so the one validator
accepts both inputs of `publicCoordination` (P4). Limits live in one exported constant `TEAM_LIMITS` in
`src/sidecar/bus/types.ts`; display caps are enforced by `publicTeams` after redaction.

## Execution instructions

**Tech stack:** TypeScript (strict, 5 compiler projects), Bun runtime and `bun:sqlite`, `bun test`, Canvas 2D browser
view, Playwright 1.64.1 (pinned) for the browser consumer, ESLint, Prettier, Knip, Fallow.

### Global constraints

- Bun runs the application and native SQLite; production has no package dependencies (`AGENTS.md`).
- Preserve strict compiler settings, deterministic lint rules, Knip and Fallow; trace HTML entries, dynamic workers and
  installed-package consumers before removing code.
- Keep tests beside their owners. Browser source must not acquire privileged Bun/Node globals.
- Checks are read-only; use `bun run format` / `bun run fix` explicitly.
- Preserve loopback/token/origin checks, identity validation, bounded reads, redaction and stale observations. Missing
  sources remain unavailable; never guess identities.
- Preserve `--no-env-file`, `bunfig.toml` environment restrictions and child/worker environment filtering.
- Browser checks use pinned Playwright and synthetic data; no real bus, controls, provider calls or MCP in tests.
- UI: immediate input feedback, no expensive work in input handlers, scope updates to affected views.
- Every new SQLite query is read-only, bounded (`LIMIT n+1` and `substr`), and degrades independently on older schemas.
- Coordination data is scoped to agents/projects already observed (exact joins only).
- No Co-Authored-By trailers, no timeline estimates, no paid/live runs or deployment.
