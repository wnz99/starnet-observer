# UI responsiveness implementation plan

Semantic revision: 2. Status: authored and self-reviewed; simplicity finding S1 incorporated; independent review and concrete user approval pending.

## Features and effects

The station should respond to deliberate clicks, keep host controls usable during updates, and retain clear agent indicators while zooming. These changes stay inside the current browser application.

### F1: Reliable canvas targets and click sequences

- Problem and current behavior: nearby pointer releases within 800 ms reuse the previous target and suppress toggles. Ignored retries extend that window. A worker's padded body can also intercept a visible repository sign.
- Proposed behavior: independent clicks toggle immediately. A browser-recognized double-click acts once on a title, sign or observatory. Its second click retains the first worker target across a focus repaint. Accepted visible title and repository plates win over padded body regions.
- Effect on the code: the pointer owner determines whether a gesture qualifies as a click; native click count distinguishes continuation from an independent gesture. The interaction owner resolves targets and dispatches actions.
- Scope and compatibility: preserve drag thresholds, pinch, slow-touch rejection, cancellation, stale painted-frame rejection, immediate worker focus and double-click platform focus. Do not delay all clicks while waiting for a double-click.
- Acceptance outcomes: clicks at 0, 600 and 1200 ms each toggle when delivered as separate native click sequences. Actual double-clicks toggle once. Clicking a drawn repository sign never selects an overlapping padded worker body.
- Execution mapping: Task 2; browser proof in Task 5.

### F2: Host controls survive rendering

- Problem and current behavior: unchanged host tabs are detached and reinserted on every content refresh. Focus disappears and a poll between pointer-down and pointer-up can cancel activation.
- Proposed behavior: preserve tab DOM attachment when membership and order are unchanged. Continue updating counts, health and selection attributes. Remove departed hosts and their listeners normally.
- Effect on the code: reuse the existing identity-aware `ui.arrange` operation in the host owner.
- Scope and compatibility: retain remembered host selection, host disappearance fallback, remote spawning eligibility and listener disposal.
- Acceptance outcomes: a focused unchanged tab remains focused; pressing, rendering unchanged content and releasing activates the intended host once.
- Execution mapping: Task 3; real browser proof in Task 5.

### F3: Status and repository indicators remain legible

- Problem and current behavior: overhead status dots appear only at overview level. Every selected-repository ring uses one theme color, so agents are indistinguishable by ring.
- Proposed behavior: show steady status dots at every level of detail, including focus and platform zoom. Give each selected agent a stable identity-based ring color. Use the same agent color for its working glow and double ring.
- Effect on the code: worker labels own status dots; frame overlays own identity coloring. Repository signs retain the repository theme color.
- Scope and compatibility: preserve status semantics, unknown status fallback, stale styling, fresh-working emphasis, root/helper coverage and exact repository IDs. Identity colors do not replace status colors or text. No theme schema or dependency changes.
- Acceptance outcomes: dots are visible above bodies at overview, intermediate, detail and maximum zoom. Titles and attention markers do not cover them. Agents in a representative 16-agent repository have distinct ring colors; colors survive repaint, reorder, selection changes and zoom. Working emphasis still depends on that agent's own freshness.
- Execution mapping: Task 4; theme screenshots in Task 5.

### F4: Local actions avoid unrelated work; remaining candidates receive measured dispositions

- Problem and current behavior: repository toggles, search, filters and selection use the same full content refresh as snapshot ingestion. This repeats floor reconciliation/serialization, couriers, mail and host work. Static-layer rebuilds across zoom buckets and repeated canvas rectangle reads are suspected costs, without measured stalls.
- Proposed behavior: use a small explicit refresh scope for local state changes. Measure complete interaction through the next painted frame with real stylesheet, fonts and artwork before and after the changes. Every scanned candidate receives evidence and a retain/fix/escalate disposition.
- Effect on the code: keep ingestion and freshness on the existing full renderer. Add direct roster/local-view refresh entry points in that owner rather than a new scheduling or caching framework.
- Scope and compatibility: page, host, arrangement, polling, stale deadlines and resume still use full reconciliation. Keep static cache and pointer coordinate handling unchanged unless profiling establishes a concrete defect and the resulting amendment passes the existing plan gate.
- Acceptance outcomes: search/filter do not rebuild or reconcile floor data; repository toggle updates roster and canvas without rebuilding floor/courier/mail state; same-page, same-host selection avoids full reconciliation. Full-theme measurements show no introduced regression, and no confirmed profile defect remains silently deferred.
- Execution mapping: Task 1 baseline, Task 5 implementation and comparison.

## High-level design and rationale

Use the smallest existing owners. `Interaction` already remembers the first painted target, and `PointerGestures` already distinguishes taps from drags and pinches. Replace elapsed-time deduplication with native click continuation information. `Hosts` already caches tab nodes; avoid replacing its unchanged child list. `WorkerLabels` already paints screen-space status dots. `FrameOverlays` already draws all selected-repository agents. `AppRenderer` remains the single owner of refreshing application presentation.

The local-refresh API has two cases, not a general dependency engine: roster-only and roster-plus-canvas. Navigation chooses them only when page and host do not change. Everything affecting snapshot provenance, freshness, topology or host continues through full refresh. This removes demonstrated redundant work without claiming that its current duration proves a stall.

Keep one private identity-to-color map in the overlay owner. On the first encounter with an identity, assign the next entry of a deterministic indexed color sequence and remember it; existing entries never change. Choose a sequence whose first 16 entries are visually distinct in both canonical art styles, and whose generated continuation does not cycle back through assigned entries at supported fixture sizes. No hash seeding, collision probing or occupied-color set is needed. The map shares the mounted view's lifetime and survives ordinary stop/start, page and camera changes. Do not add persistence or publish identities. Colors identify agents alongside existing status/text cues; unlimited perceptual uniqueness is not promised.

Risks and safeguards:

- Native pointer releases do not reliably carry click counts. Read `MouseEvent.detail` on `click`, not `PointerEvent.detail` on `pointerup`. Browser integration evidence is required.
- Pointer capture can produce a click after a drag. Dispatch only when the completed gesture explicitly qualifies; clear eligibility on movement, pinch, cancellation, slow touch, reset and disposal.
- First-click focus can move the camera. A continuation uses the first target rather than a new hit test. A vanished worker must not turn into a floor/platform action.
- Local refresh must not bypass stale transitions or pending resume proof. It consumes current admitted state and must not update freshness/bookkeeping fields.
- Dot/title overlap is a rendering concern. Reserve a separate vertical lane, with a constant CSS-pixel dot size at all zooms; inspect both station and office art.
- Profiling is synthetic evidence tied to the tested browser, scene and machine. Absolute latency is recorded, not made a flaky CI threshold. A measured unexplained stall requires a bounded plan amendment before claiming F4 complete.

## Data-flow analysis

| Stage | Input and source | Processing and owner | Output or side effect | Material failure handling |
| --- | --- | --- | --- | --- |
| Gesture eligibility | Native pointer sequence | `PointerGestures` records eligible release; `Interaction` consumes next canvas click | One accepted click, with native continuation count | Drag, pinch, cancel and slow touch leave no eligible action |
| Target dispatch | Accepted screen point plus current painted regions or remembered continuation | `Interaction.targetsAt` prioritizes accepted title/sign, body, observatory and ship | Exact ID callbacks; first target retained for genuine double-click | Reject stale plate regions; vanished worker never substitutes another target |
| Host rendering | Admitted host sources and selected host | `Hosts.tab` updates node; `ui.arrange` compares identity/order | Unchanged controls remain attached | Evict disappeared hosts and listeners; retain existing fallback selection |
| Agent indicators | Worker ID, status, freshness and anchors | `WorkerLabels` paints dot; `FrameOverlays` looks up stable color | Screen-space status plus identity-colored repository emphasis | Unknown status keeps existing fallback; stale working never gains live glow |
| Local refresh | Repository, filter, search or same-page selection change | Navigation chooses a bounded `AppRenderer` method | Roster and, when needed, canvas invalidation | No work after inactive/disposed state; full refresh for topology/freshness/host/page changes |
