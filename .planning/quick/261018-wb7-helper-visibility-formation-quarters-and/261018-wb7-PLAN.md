# Helper crew consistency implementation plan

Semantic revision: 3. Planning and review only; implementation awaits user approval.

## Features and effects

The room, helper list and crew statistics will describe the same displayed crew. Historical token usage remains a separate observation. Each project room gains one quarters area, and helpers use it for evidenced arrivals and departures.

### F1: One displayed crew scope (R1, R4, R5)

- Problem and current behavior: retained helpers without a collision-free station appear in the list and deck totals. Station totals count retained records independently of the scene.
- Proposed behavior: use actual scene placement to choose crew rows. List-only helpers leave the live roster. Deck counts cover displayed crew on that deck; station totals cover displayed crew across decks and observed hosts. Host tabs and roster filters narrow that same population. Search and status filters do not alter station totals.
- Effect on the code: reuse room placement to expose one projection, then feed roster and counts from it. Preserve raw rows for transcript resolution and historical usage.
- Scope and compatibility: an avatar is a display choice, not proof of a running process. Native pane rows remain present even when their helper station cannot be placed. Ghost relay crew remain outside observed totals.
- Acceptance outcomes: a synthetic version of the audited inventory has 12 pane agents and eight helper avatars, 20 displayed crew, and no `+56 helpers in list`. Status categories use precisely those 20 rows. Numbers are fixture assertions, not production constants.
- Execution mapping: Tasks 1, 3 and 4.

### F2: Sustained compact following (R2)

- Problem and current behavior: formation supports pairs and constrictions, but the reported experience is a long line. Existing tests accept limited successful windows.
- Proposed behavior: eligible helpers sustain compact pairs in open space, enter ordered single file only where the entire paired envelope is unsafe, and regroup after clearance. A resting idle parent holds its compact group rather than sending followers back to their desks.
- Effect on the code: repair existing formation/history/actor intent ownership. Keep deterministic ordering, bounded trails and collision checks.
- Scope and compatibility: own working/waiting states override following. Stale evidence freezes ambient motion. Nested helpers stay on their exact parent’s platform.
- Acceptance outcomes: repeated room walks, rests, turns and narrow passages sustain compact groups; all eight helpers traverse constrained passages safely and regroup. No test may weaken obstacle or containment assertions.
- Execution mapping: Task 2; Task 3 adds lifecycle intent precedence.

### F3: Quarters and truthful helper lifecycle (R3)

- Problem and current behavior: helpers begin at stations; confirmed closed helpers freeze there. No quarters exist.
- Proposed behavior: each rendered project room, including an annex, has one marked quarters area. A newly evidenced helper starts there and walks to its exact parent. A displayed helper positively confirmed killed/closed returns there and disappears after arrival. Completed tasks remain displayed and eligible for following.
- Effect on the code: add bounded browser presentation state and explicit movement intents, reusing room geometry and navigation. Departure completion updates the projection once.
- Scope and compatibility: first load, recovered connection and historical records do not replay starts or deaths. Each observation source recovers independently, including sources with no rows; healthy hosts continue their valid transitions. Unknown, disappearance and stale observations never become closure. Native panes remain authoritative pane crew; only synthetic helper avatars disappear on helper closure. No process controls or history panel are added.
- Acceptance outcomes: deterministic fresh start/close sequences animate once; completion, unknown and stale sequences never depart. Reduced motion applies final presentation state immediately. Parent loss or room removal clears presentation safely without inventing a killed event.
- Execution mapping: Task 3.

### F4: Evidence and historical usage labels (R6, R7, R8)

- Problem and current behavior: `verified`, `Tokens` and `sessions complete` are easy to read as live presence, current work or task completion.
- Proposed behavior: label crew as displayed; label verified helper links as relationship evidence and state that running presence is unconfirmed. Tokens say cumulative session-history usage and explicitly include hidden retained helpers. Coverage says complete/partial/unavailable usage data. Cached input explains provider semantics without claiming billing totals.
- Effect on the code: change existing formatting, statistics and documentation. Preserve server aggregation and provider counter extraction.
- Scope and compatibility: cumulative usage covers currently retained, identity-eligible histories, not all-time usage or a sum of every session ever seen. Counter freshness and partial/unavailable states remain visible.
- Acceptance outcomes: cached input is never added again to input totals; Codex cumulative counters and Claude message deduplication retain current semantics. Screen-reader and visible labels make the crew/history distinction clear.
- Execution mapping: Tasks 1 and 4.

## High-level design and rationale

Retain the observer’s bounded raw session collection. Do not filter historical rows at the sidecar: they carry legitimate usage and inspection evidence. The browser owns avatar placement, so its placement output also owns displayed crew membership.

Expose room-level crew placement without building entire scenes for every page. Reuse `helperWorkers` and the same room dimensions/sections as `buildRoom`; do not duplicate station validity checks. `Floor` keeps an all-deck projection, while the current scene remains page-specific. Preserve the existing floor cache and row DOM reconciliation.

Keep one small helper-presentation owner inside `Floor`, with no storage or background polling. It tracks only current displayed transitions and bounded closed tombstones. Movement owns path progress; the presentation owner owns whether an avatar remains part of crew. One settlement callback schedules a normal render after a return completes. No DOM reconciliation runs on every animation frame.

Keep usage and coverage from the existing sidecar aggregate. Derive only display counts/statuses from projected rows, using the existing freshness rules. Never turn identity verification into proof of running presence.

- Design choices: reuse `Layout`, room placement, `FormationPlanner`, `ActorState`, `Totals` and `createRowFormat`. No additional service, persistent lifecycle database, provider probe, shared aggregation framework or independent count cache.
- Risks and safeguards: station-slot reassignment, nested parent visibility, page switches and geometry changes can affect membership. Recompute membership only with changed layout/content, preserve represented IDs where valid, and test those transitions. Departures retain their occupied station until settled, preventing premature replacement.
- Arrival evidence: require a previously unseen, verified synthetic helper with a finite assignment/spawn timestamp newer than its own source's preceding accepted fresh observation and no later than that source's accepted observation. A task-running event alone does not prove birth. Without this evidence, place the helper normally without an arrival animation.
- Retention: at most 64 active helper transitions, matching current helper admission bound. Keep at most 256 closed tombstones, oldest first. An explicitly closed raw row is always ineligible for a fresh avatar even after tombstone eviction. Reappearance of an unknown old row cannot trigger a start without a new qualifying spawn timestamp.
- Lifecycle precedence: confirmed closure, entering, own working/waiting, following/holding, stationary fallback. Stale source evidence freezes presentation movement and does not create transitions. Keep observation baselines per source, using the existing source map even when it has no rows. On a source's recovery, seed only its baseline and settle only its prior transients without replay. A global observation failure or page resume requires all sources to rebaseline. Retained returns use their own source's current health after their raw row disappears; an old row timestamp cannot renew or permanently freeze that validated return.
- Compatibility: raw `aggregate.agents` remains the sidecar’s historical observation contract; the UI stops labeling it displayed crew. Usage, identity resolution, controls and remote transport contracts remain unchanged.
- Open decisions: none required to author this design. Visual quarters styling and exact safe coordinates are implementation details subject to geometry assertions and visual review. The conservative arrival rule intentionally skips uncertain animations.
